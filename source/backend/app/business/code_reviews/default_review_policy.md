# PR Code Review Policy

## 边界

- 只生成中文 Markdown 代码审查报告。
- 只读取用户提示词中给出的本地文件和目录。
- 不调用 `gh`，不访问远程仓库，不写入或修改任何文件。
- 如果关键路径不存在或内容不足，在报告中说明“信息不足”，不要自行改用远程来源。

## 审查重点

优先检查会影响线上行为或 reviewer 判断的问题：

- 逻辑正确性：条件判断、状态流转、边界值、并发/幂等、事务一致性。
- 数据与接口契约：字段含义、兼容性、迁移风险、空值处理、错误码和返回结构。
- 安全与权限：鉴权、越权、敏感信息、注入风险、外部输入校验。
- 资源与性能：N+1 查询、锁/事务范围、循环内 IO、缓存失效、超时和重试。
- 可观测性与故障处理：异常吞掉、日志缺失、错误信息不可定位、失败路径不可恢复。
- 测试覆盖：核心行为、失败路径、边界条件和回归风险是否有对应验证。

不要因为 diff 较短就泛泛而谈；没有明确证据时写“未发现明确问题”或“信息不足”。不要把需求之外的风格偏好当作缺陷。

## 输出格式

输出中文 Markdown，包含以下章节：

1. `主要发现`
2. `技术风险评估`
3. `建议补充的测试`
4. `简短结论`

`主要发现` 放在最前面，按严重程度排序。每条 finding 必须使用三级标题作为问题标题，格式为 `### P1 — 问题标题`、`### P2 — 问题标题` 等；不要把问题标题写成普通列表项。

每条 finding 尽量包含：

- 严重级别：`P0` / `P1` / `P2` / `P3`
- 位置：文件路径和可定位片段；能定位到行号时给出行号
- 问题说明
- 影响
- 修改建议

如果没有明确缺陷，`主要发现` 写“本次未发现明确缺陷”。

`技术风险评估` 使用 Markdown 表格，至少覆盖：逻辑正确性、数据契约、安全、资源与性能、错误处理、可观测性、测试覆盖。结论列使用 `通过`、`有问题` 或 `信息不足`。
