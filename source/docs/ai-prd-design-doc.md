## 一、为什么做这个

### 背景

**传统 RAG 效果不好**
RAG 使用了庞大而笨重的向量数据库，把文本切分后索引，以期达成语义搜索的效果，但实际上缺乏整体逻辑，只是一些语义碎片。

**大家在用 AI，但用的是各自的上下文**。

产品在问 ChatGPT 业务规则，研发在用 Claude 写代码，测试在手动整理用例——每个人都在重复描述同样的背景信息，结论也难以对齐。

更深的问题是：**公司积累的业务知识、历史需求、代码逻辑，和 ai 对话是没有互动的**。

### 前身的教训

这个项目的前身是「业务文档协作系统」，当时的思路是：用 AI 从代码反推业务文档，再让产品以此为模板写需求。

做完发现根本行不通——代码反推出来的文档太偏技术，产品看不懂，也用不起来。

但这件事验证了一个方向：**如果能让产品和研发共享同一套业务知识，AI 提效的效果会很明显**。这就是 ai-prd 的出发点。

### 这次的转变

从「文档工具」变成「协作工具」。

不再是给某一类人用的工具，而是把产品、研发、测试的工作知识连接在一起，让 AI 成为跨部门协作的中间层。

---

## 二、产品定位

**ai-prd 是一个面向产研团队的 AI 协作平台。**

核心逻辑很简单：把需求文档、业务规则和代码库接入同一个对话入口，让每个人都能用上彼此的经验，而不是各自重新描述一遍背景。

目标用户：产品、研发、测试、设计（当前阶段主要是前三类）。

## 三、解决什么问题

### 场景 1：产品写需求

以前：脑子里有个方向，但不确定现有的业务规则是什么，要去翻历史需求文档或者问研发。

现在：直接在对话里 @业务文档，AI 帮你回忆相关规则，写出来的需求自然和现有逻辑一致。

### 场景 2：研发评审需求

以前：拿到需求文档，看不懂产品意图，要来回问。

现在：直接用产品的 PRD Skill 解析需求，或者让 AI 结合代码库告诉你这个需求影响哪些模块。

### 场景 3：测试生成用例

以前：需要同时打开需求文档、业务规则文档和代码，手动整合信息再写用例。

现在：@需求文档 + @业务知识，让 AI 帮你生成覆盖边界条件的测试用例。

### 场景 4：新人上手

以前：想了解某个业务域，不知道从哪里找文档，问人也问不到全貌。

现在：知识库里有按域分类的业务文档，直接问 AI，可以快速建立业务模型。

### 场景 5：了解当前实现逻辑

这可能是是需求最强烈的场景。

以前：当一名非技术人员，想了解当前实现的时候，它目前唯一的方法，就是询问研发，而即使是研发，面对自己不够熟悉的领域，也要翻很久代码。

现在：可以直接通过 ai 来了解当前实现，甚至直接比对实现和需求直接的差异，给出复杂性评估。

## 四、核心功能

### 4.1 AI 助手

这是整个平台的核心入口。

背后接的是 Claude Code 和 Codex，会话走流式返回，交互体验和普通 AI 对话一样流畅。之所以选择封装而不是让大家自己配，是因为配置 AI 本身有门槛，而且每个人配置不同，协作时上下文没法对齐。

**一个关键设计：上下文四层模型**

每次 AI 对话的背后，上下文其实有四种来源：

| 层级 | 是什么 | 例子 |
|------|--------|------|
| 会话范围 | 这个会话长期挂载的知识域 | 激活「@业务文档」后，这个会话每轮都带着整个业务文档域 |
| 本轮指定 | 这一轮你主动 @ 的内容 | 这轮回答专门 @了某个具体需求文档 |
| 已读取上下文 | AI 实际读了哪些内容 | 后端有记录，当前界面暂未展示 |
| 来源 | AI 回答引用了哪些片段 | 每条回答都有可追溯的证据 |

这四层分离是为了解决一个很实际的问题：AI 用了哪些信息、为什么给出这个结论，要能查得到，不能是黑盒。

### 4.2 知识库

知识库分三类，对应三种不同的知识来源：

**需求文档**：从 ClickUp 自动同步。产品在 ClickUp 里写需求，系统定时拉取，直接可以在对话里引用，不需要手动导入。

**业务文档**：按业务域手动维护的规则文档（比如 P2P 交易规则、用户 KYC 流程等）。把公司多年积累的业务逻辑，整理为结构化的表达。

**代码库**：挂载 Git 仓库，自动同步。研发可以让 AI 直接结合代码库分析问题，产品也可以让 AI 对照代码解释某个功能的实际行为。

三类知识都会记录同步状态和变更历史，知道什么时候更新、更新了什么。

### 4.3 @ 引用机制

在对话框里输入 `@`，会弹出知识库的文件列表，直接选择你想引用的内容。

知识库文件可能有上万个，不能每次都从服务器加载，所以用了一个索引方案——页面首次加载时异步拉取索引并缓存在内存里，输入时本地过滤，速度快，不影响页面响应。

### 4.4 Skill 共享

Skill 是把一类分析任务沉淀成可复用模板的机制。

举个例子：
- 产品有「PRD 评审」Skill，用来检查需求文档是否完整
- 研发有「技术评审」Skill，从实现可行性角度审需求
- 测试有「业务测试用例生成」和「需求实现测试点」Skill

这些 Skill **可以跨部门使用**。产品可以跑研发的技术评审 Skill 来自检需求，研发也可以用产品的 PRD Skill 来快速解析需求背景。

Skill 通过文件系统发现（放在 `.claude/skills/` 目录下），研发直接提交文件就能上线新 Skill，不需要走数据库配置。

### 4.5 会话分享

一键分享对话，支持公开分享（全员可看）和指定成员分享。

分享的应用场景：
- 产品和研发对某个需求有分歧，把 AI 给出的分析结论分享出来一起看
- 某次对话产出了有价值的业务梳理，分享出来供团队参考
- 测试把生成的用例分享给研发确认

分享页面支持评论，可以在同一个对话上下文里讨论，不用开新的沟通渠道。

## 五、技术架构

### 整体结构

```
┌─────────────────────────────────────────┐
│               浏览器端                   │
│   对话界面  /  知识库浏览  /  Skill 中心  │
│   @ 智能提示（本地索引过滤）              │
└─────────────────┬───────────────────────┘
                  │ HTTP / SSE（流式）
┌─────────────────▼───────────────────────┐
│             后端服务（FastAPI）           │
│   会话管理  /  消息处理  /  分享  /  认证 │
│   知识库浏览接口  /  文件同步任务         │
└──────┬──────────────────────────────────┘
       │                    │
┌──────▼──────┐    ┌────────▼────────────┐
│  AI 运行时   │    │      知识库层        │
│ Claude Code │    │ 需求文档（ClickUp）  │
│   / Codex   │    │ 业务文档（手动）     │
│ 多进程隔离   │    │ 代码库（Git 同步）   │
└─────────────┘    └─────────────────────┘
```

**几个关键设计决策：**

**为什么知识用文件系统而不是向量数据库**

向量检索听起来更"AI"，但不具有整体性，实际上丢失了文件中的结构信息。

**为什么要做 FileTreeCache**

知识库文件多了之后，每次接口请求都扫描文件系统会很慢。缓存设 5 分钟 TTL，后台异步刷新，对用户来说接口响应不受影响，数据也不会太陈旧。

**为什么 AI 用子进程隔离**

每次 AI 调用都通过 subprocess 启动独立的 Claude Code 或 Codex 进程，一次调用出问题不会影响其他会话，资源也不会互相抢占。

**为什么用 Google OAuth**

团队都在用 Google Workspace，账号绑定公司邮箱，不需要单独管理账号体系，部门准入也可以通过 Google 组织信息来控制。

### 数据模型（简版）

核心就两张逻辑表：

- **会话（Session）**：有所有者、有名字、有状态、可以挂载知识上下文
- **消息（Message）**：属于某个会话，记录内容、来源引用、执行轨迹

其他都是围绕这两个核心扩展的：分享、评论、图片上传、上下文挂载记录。

## 七、后续方向

**Skill 体验深化**

现在 Skill 可以展示和发起，但跨部门共享的使用体验还可以更顺滑——比如在对话里直接选 Skill、Skill 执行结果的结构化展示。

**更细粒度的权限控制**

目前是按部门整体准入。后续可以按知识库域、按 Skill 类型做更细的控制，比如某类敏感业务规则只对特定角色开放。

**其他知识库接入**

当前知识库只涉及产研，后面可以考虑接入设计（Figma）和测试，还有线上页面的访问。

**多工作区支持**

目前是单一工作区。如果不同产品线或不同团队需要隔离知识库和 Skill，可以扩展为多工作区模式，包括个人工作区

**定时任务**

目前只有被动地接受问询，后面可以实现更自主地定时任务，长期监控和完成工作

## 八、附录：核心概念速查

| 概念 | 说明 |
|------|------|
| 会话（Session） | 一次完整的对话上下文，可以持续挂载知识 |
| 知识对象 | 需求文档 / 业务文档 / 代码知识，三类知识来源 |
| 挂载 | 把某个知识域关联到当前会话，后续每轮都会带入（当前支持域级别：需求/业务/代码） |
| 本轮指定（@ 引用） | 单次对话中临时指定的引用，不影响会话范围 |
| Skill | 沉淀为模板的分析任务，可跨部门调用 |
