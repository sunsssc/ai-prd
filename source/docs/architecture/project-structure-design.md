# ai-prd 项目结构设计

## 1. 文档信息

- 项目名称：ai-prd
- 文档名称：项目结构设计
- 文档版本：V1.0
- 文档日期：2026-04-11
- 文档状态：草案

---

## 2. 背景

`ai-prd` 的定位已经从“业务模型文档系统”调整为“连接需求、业务文档和代码知识的轻量 AI 工具”。

新的产品方向强调以下原则：

- AI 助手是核心入口
- Skill 是能力组织方式，而不是多个彼此割裂的大模块
- 需求文档、业务文档、代码知识是三类核心上下文
- 系统保持轻量、直接、可扩展
- 应用源码、知识资产、运行时数据必须分离

因此，项目在目录结构上不再延续旧系统“源码仓 + 内嵌文档仓 + 运行数据混放”的方式，而是拆分为更清晰的两层：

- `source/`：应用源码、配置、设计文档、基础设施定义
- `workspace/`：知识库内容、同步产物、运行时数据、外部代码仓挂载点

---

## 3. 设计目标

本次项目结构设计希望解决以下问题：

1. 避免将知识库和运行时数据混入代码仓库
2. 支持未来同时管理多类知识源
3. 让 Skill、同步、AI 对话、知识库管理具备清晰边界
4. 为后续大规模重构保留足够扩展空间
5. 让本地开发、Docker 部署和后续远程化部署拥有一致的目录语义

---

## 4. 总体结构

```text
ai-prd/
├── source/
│   ├── frontend/
│   ├── backend/
│   ├── packages/
│   ├── scripts/
│   ├── docs/
│   └── infra/
└── workspace/
    ├── knowledge/
    └── runtime/
```

### 4.1 source

`source/` 用于承载所有需要进入源码版本管理的内容，包括：

- 前后端应用源码
- 共享包与协议定义
- 工具脚本
- 产品文档与架构文档
- Docker / Nginx / 部署配置

### 4.2 workspace

`workspace/` 用于承载运行环境相关内容，不作为主源码的一部分。其下内容可以按实际场景选择：

- 不纳入 Git 管理
- 独立 Git 管理
- 由外部系统同步生成
- 运行时动态生成

这使得系统不会再把“知识资产”和“应用源码”混在同一个仓库语义下。

## 5. source 目录设计

### 5.1 frontend / backend

```text
source/
├── frontend/
└── backend/
```

#### frontend

前端应用目录，建议基于 React 实现，按产品信息架构组织页面，而不是沿用旧系统的“文档管理中心”思路。

推荐优先采用“AI 助手作为单一主入口”的结构，而不是把知识库、Skill、设置都做成彼此割裂的主工作台。

更具体地说，建议前端界面遵循以下原则：

- 首页默认进入 AI 助手会话页
- 左侧负责会话切换、新建会话和最近历史
- 中间区域负责对话、追问、结果展示和可溯源引用
- 知识库管理、Skill 管理优先作为会话侧边抽屉或二级管理面板出现
- 只有在需要做批量配置、权限设置、全局同步管理时，再进入独立管理页

因此，推荐围绕以下页面和面板组织：

- AI 助手
  - 新建会话
  - 历史会话
- 会话右侧工作台
  - 当前上下文
  - 知识库挂载与同步状态
  - Skill 可见性与启停
- 知识库管理页
  - 需求文档
  - 业务文档
  - 代码仓与索引
- Skill 管理页
- 设置

建议的前端目录可按 React 应用习惯组织，例如：

```text
source/frontend/
├── src/
│   ├── app/
│   ├── pages/
│   ├── features/
│   ├── components/
│   ├── hooks/
│   ├── services/
│   ├── stores/
│   └── styles/
├── public/
└── package.json
```

其中建议按以下原则理解：

- `app/`：应用入口、路由、全局 Provider
- `pages/`：页面级容器
- `features/`：按产品能力拆分的前端模块，如 assistant、knowledge、skills、settings
- `components/`：跨页面复用组件
- `services/`：前端请求封装与 BFF/后端接口适配
- `stores/`：客户端状态管理

#### backend

后端应用目录，建议基于 FastAPI 实现，承担以下职责：

- AI 对话接口
- 知识库管理接口
- Skill 调度接口
- 同步任务接口
- 配置与权限接口
- 会话持久化与状态恢复

建议后续在 `backend` 内继续拆分为：

- `app/api/`：FastAPI 路由层
- `app/core/`：配置、认证、基础设施能力
- `app/business/assistant/`：AI 助手
- `app/business/knowledge/`：知识库聚合
- `app/business/codebase/`：代码知识相关业务能力
- `app/settings/`：系统级业务配置
- `app/integrations/`：外部系统接入，例如 ClickUp、Git、Google、LLM
- `app/jobs/`：同步、索引、异步任务和定时任务
- `app/models/`：结构化数据

建议的后端目录可按 FastAPI 项目习惯组织，例如：

```text
source/backend/
├── app/
│   ├── api/
│   ├── core/
│   ├── business/
│   ├── integrations/
│   ├── jobs/
│   └── models/
├── tests/
└── pyproject.toml
```

其中建议按以下原则理解：

- `business/`：产品真正提供给用户的业务能力
- `integrations/`：外部系统适配层，负责“怎么接”
- `jobs/`：任务执行与调度层，负责“什么时候跑、怎么跑”

#### 会话上下文挂载与来源记录机制

在 AI 助手会话页中，需要明确区分以下四层信息，避免把“会话长期范围”“本轮显式指定”“本轮实际读取”“回答证据引用”混为一谈：

- `当前会话范围`：会话级状态，表示这场会话默认在哪些粗粒度范围内工作
- `本轮指定`：轮次级输入，表示用户这一轮通过手动 `@` 或页面选择显式带入了哪些上下文对象
- `已读取上下文`：轮次级执行记录，表示本轮回答前系统实际推断并读取了哪些对象
- `来源`：回答级证据，表示当前这段结论具体依据了哪些章节、文档片段或代码文件

这四层信息的设计意图如下：

- 会话长期范围由应用侧显式保存，不应从 AI 返回内容中反向推断
- `本轮指定` 用来回答“用户这一次明确要求看什么”，与长期范围不是一回事
- `已读取上下文` 用来回答“系统这一次实际打开了什么”，允许包含 AI 自动推导出的范围或对象
- `来源` 用来回答“这句结论具体依据什么”，应比 `已读取上下文` 更接近最终证据单元
- Claude Agent SDK 负责消费上下文、维持会话历史、执行工具调用；应用侧负责把这些对象组织成可展示、可恢复、可审计的业务模型

建议会话中涉及的上下文对象至少包括：

- 需求上下文，例如 `PRD-2418`
- 业务文档上下文，例如“营销域 / 优惠券规则”
- 代码上下文，例如“代码仓 + 分支/提交 + 可选路径范围”
- Skill 上下文，例如“需求评审”
- 可选的工作区上下文，例如业务域、项目组或产品线

建议进一步把“来源方式”和“对象粒度”拆开理解：

- 来源方式
  - 用户手动 `@`
  - 页面选择或工作区默认带入
  - AI 在本轮执行过程中自动推导
- 对象粒度
  - 粗粒度范围，例如业务域、规则集、代码仓/分支、路径范围
  - 具体对象，例如某个 PRD、某份规则文档、某个代码文件
  - 最小证据单元，例如具体章节、代码行段、文档片段

界面展示粒度建议如下：

- `当前会话范围`
  - 仅展示粗粒度范围，例如“营销域”“优惠券规则”“repo/release/bonus-coupon”“coupon/**”
  - 不直接堆叠具体文件、具体章节，避免把长期范围和本轮证据混在一起
- `本轮指定`
  - 展示用户本轮显式带入的对象，并标记来源方式，例如“手动 @需求”“页面选择”
  - 可以展示具体文件或具体 PRD，因为这层回答的是“这轮明确要求看什么”
- `已读取上下文`
  - 同时容纳 AI 自动推导出的范围和实际读取对象
  - 推荐把“本轮推断范围”和“实际读取对象”拆成两组展示
- `来源`
  - 应尽量落到最小证据单元，例如 `PRD-2418 §4.2`、`coupon_service.py:120-168`
  - 不再重复会话级范围信息

建议按以下方式理解 Claude Agent SDK 与应用侧的职责边界：

- Claude Agent SDK 原生提供：`session_id`、会话恢复、历史消息、工具调用、Skill 发现、运行时环境信息
- Claude Agent SDK 不直接提供：业务意义上的“会话已挂载上下文对象”模型
- 因此，`ai-prd` 需要在应用层维护一套独立的会话上下文挂载记录，并在每轮调用 Agent 前组装输入

建议采用如下数据分层：

- `session_context_mounts`：会话级挂载关系，描述当前会话长期绑定了哪些上下文对象
- `turn_context_requests`：轮次级显式指定，描述本轮由用户手动 `@` 或页面选择带入了哪些对象
- `turn_context_usage`：轮次级读取记录，描述本轮实际推断并读取了哪些对象
- `answer_citations`：回答级引用记录，描述最终答案引用了哪些证据

其中四者的产生方式应分别如下：

- `session_context_mounts`
  - 来源于用户显式挂载、从工作区自动带入、或恢复历史会话时回放
  - 由应用数据库或会话状态存储持久化
  - 前端展示时应优先归一化为“当前会话范围”所需的粗粒度表达
- `turn_context_requests`
  - 来源于本轮输入中的手动 `@`、页面勾选、或其他显式选择动作
  - 需要记录 `origin`，至少区分 `manual_mention` 与 `page_selection`
- `turn_context_usage`
  - 来源于本轮调用前的上下文解析，以及检索工具、文档读取工具、代码检索工具的执行结果
  - 需要记录 `origin`，至少支持 `explicit` 与 `ai_inferred`
  - 应由应用侧在工具调用链路中记录，而不是依赖模型自由生成文案
- `answer_citations`
  - 来源于回答阶段的证据引用
  - 可优先使用 Claude 的 citations 能力；如知识源形态复杂，也可由应用定义统一的引用结构

推荐的最小读取链路如下：

1. 用户在会话中挂载或切换长期上下文对象
2. 应用保存 `session_context_mounts`
3. 用户发起提问时，应用解析本轮手动 `@` 和页面选择，写入 `turn_context_requests`
4. 应用根据 `session_context_mounts` 与 `turn_context_requests` 组装候选上下文
5. Agent 在回答过程中通过检索/读取工具访问需求、业务文档和代码知识，并产生必要的 AI 推断范围
6. 应用根据实际工具执行结果写入 `turn_context_usage`
7. 回答生成后，系统输出 `answer_citations` 并展示在消息卡片中

因此，原型页中的四块展示建议分别读取以下数据：

- `当前会话范围`：读取 `session_context_mounts`，并做粗粒度归一化展示
- `本轮指定`：读取当前轮次的 `turn_context_requests`
- `已读取上下文`：读取当前轮次的 `turn_context_usage`
- `来源`：读取当前回答的 `answer_citations`

需要特别强调：

- 不应以某一轮回答里是否出现某个“来源”来判断该上下文是否仍然属于当前会话范围
- 同一会话中，某个范围可能长期存在，但只在部分轮次被实际读取
- 同一轮中，用户显式指定的对象不一定都会被实际读取
- 同一轮中，AI 可能推导出新的读取范围，但这些推导结果不应自动回写成长期会话范围，除非用户确认或系统显式挂载
- 同一轮中，实际读取过的对象也不一定全部出现在最终展示给用户的来源标签中


### 5.3 Skills 管理

`ai-prd` 使用 Claude Code SDK / Claude Agent SDK 的 Skill 机制时，应采用“文件系统发现”模式，而不是在应用代码中自行维护一套 Skill 注册中心。

这意味着：

- Skill 本体是文件系统中的 `SKILL.md`
- SDK 根据配置自动发现可用 Skill
- 应用负责决定“从哪里加载”“哪些 Skill 对当前产品可见”“是否在界面中展示和启停”
- 应用不需要在 `app/business/` 下维护一个 `skills/` 目录来承载 Skill 本体

建议的项目级 Skill 目录如下：

```text
source/
└── .claude/
    └── skills/
        ├── requirement-review/
        │   └── SKILL.md
        ├── test-point-generation/
        │   └── SKILL.md
        └── code-impact-analysis/
            └── SKILL.md
```

建议按以下层次理解 Skill 管理：

- `source/.claude/skills/`：团队共享的项目级 Skill，纳入源码版本管理
- `~/.claude/skills/`：个人级 Skill，不纳入项目源码
- `source/packages/skill-sdk/`：Skill 元数据、调用约定、前后端展示协议、SDK 适配代码
- `app/business/assistant/`：在会话中决定何时提示用户使用 Skill，或如何结合上下文调用 Skill
- `app/business/settings/`：管理哪些 Skill 在产品层面可见、可用、可推荐

需要特别区分的几点：
- Skill 的“发现与调用”主要由 Claude SDK 负责，不应重复实现一套程序内注册机制
- Skill 的“产品管理”仍然需要系统负责，例如可见性、启停状态、说明文案、输入要求展示

对 `ai-prd` 而言，建议产品和工程侧分别承担这些职责：
- SDK 负责：扫描 Skill 文件、按描述匹配、在会话中自动调用
- 项目源码负责：约束目录位置、管理元数据、控制 UI 展示、封装运行参数

运行时建议遵循以下配置原则：
- Agent `cwd` 指向 `source/`
- 启用 `project` 级 setting source，以便加载 `source/.claude/skills/`
- 如需要支持个人 Skill，再额外加载 `user` 级 setting source
- `allowed_tools` 中显式启用 `Skill`

因此，Skill 在 `ai-prd` 中应被视为“项目资源 + 平台能力配置”，而不是“后端业务模块目录”。

## 6. workspace 目录设计

### 6.1 knowledge
```text
workspace/knowledge/
├── requirements/
├── business-docs/
└── code/
```

#### requirements
用于存放从 ClickUp 或其他需求源同步下来的需求文档内容。

特点：

- 是“需求知识库”本体
- 可以由同步任务自动更新
- 可以后续支持增量同步和状态追踪
- 默认不应直接与主源码仓绑定

#### business-docs
用于存放业务文档知识库。

特点：

- 可以作为独立文档仓库存在
- 可以保留版本控制能力
- 与应用源码解耦
- 未来如需迁移到独立远程仓库，成本较低

#### code
用于存放源代码本体。
workspace/knowledge/code
├── coinex-backend/
├── coinex-comment/
└── coinex-admin-frontend/
└── ...


### 6.2 runtime
```text
workspace/runtime/
├── db/
├── cache/
├── logs/
├── sessions/
└── sync-state/
```

各目录职责如下：

- `db/`：本地数据库文件
- `cache/`：临时缓存、检索缓存、渲染缓存
- `logs/`：应用日志、同步日志、任务日志
- `sessions/`：会话快照、挂载上下文、轮次级读取记录等可恢复状态
- `sync-state/`：知识同步游标、索引任务状态、外部源增量同步记录

该层内容本质上属于运行时数据，不应与知识文档或源码混放。

## 8. 配置原则
建议后续配置不要再围绕单个 `DOCS_REPO_PATH` 组织，而是改为按职责拆分：

- `APP_HOME`
- `RUNTIME_ROOT`

这样做的好处是：

- 每类目录职责明确
- 配置更容易迁移到 Docker 或远程环境
- 后续支持多环境部署时更稳定

---

## 9. 后续重构建议

建议按以下顺序推进：

1. 先在 `source/` 中搭建新的前后端骨架
2. 明确新的配置体系和环境变量命名
3. 重新抽象知识对象模型
4. 建立 Skill 注册与执行框架
5. 接入需求同步能力
6. 再逐步接入业务文档和代码知识能力
7. 最后再考虑迁移旧系统中可复用的模块

这样可以避免把旧系统的结构性问题整体带入新项目。

---

## 10. 当前结论

`ai-prd` 应被视为一个新的产品工程，而不是旧“业务模型文档系统”的简单重命名版本。

因此，项目目录层面应明确坚持以下原则：

- 源码与知识资产分离
- 知识资产与运行时数据分离
- Skill 作为平台能力组织方式
- AI 助手作为默认入口
- 知识库围绕“需求 / 业务文档 / 代码”三类上下文展开

这份结构设计文档将作为后续模块设计、配置设计和初始化脚手架设计的基础。
