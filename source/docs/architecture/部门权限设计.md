# 测试造数部门权限设计

## 1. 文档目的

为测试造数能力增加可由 Admin 配置的部门权限，避免继续使用“所有普通成员都可用”或“只有组织管理员可用”的粗粒度判断。

本文只描述设计，不包含本地实现、数据库变更或部署操作。

## 2. 本期范围与明确取舍

### 2.1 本期目标

- Agent 使用权限、业务能力权限、资源范围权限三者分离。
- Admin 可以按部门授予或收回测试造数能力。
- 首期只配置一个业务权限项：`UAT 环境控制`；它控制用户能否使用系统当前开放的 UAT 环境和造数任务。
- 权限判断由后端统一完成，并在准备计划和实际执行时分别校验。
- 权限判断结果可解释、可审计，便于排查“为什么某用户没有权限”。

### 2.2 本期不做

- 不增加 `environment_key`，不按 UAT、测试 1、测试 2 等环境分别配置用户权限。
- 不把环境列表放入 Admin 权限策略；`TEST_DATA_ALLOWED_ENVIRONMENTS` 仍是系统级的造数平台开放范围。
- 不在 Admin 中按测试造数平台的单个任务代码配置权限；未来确有需要时再增加任务级范围。
- 不做通用 RBAC、策略表达式、复杂 Allow/Deny 优先级或多层审批流。
- 不允许管理员手工修改用户部门；部门归属以 OA 目录为准。

因此，本期的权限语义是：

> 某部门是否可以使用 `UAT 环境控制` 能力；获得授权后可使用系统当前开放的 UAT 环境和造数任务，系统级白名单与黑名单仍然有效。

如果以后需要“研发中心只能访问 UAT，而其他环境由其他部门访问”，再把环境作为策略范围扩展，不在本期预埋。

## 3. 与现有权限的关系

现有权限分为两类：

1. Agent 权限：决定用户能否进入和使用 ai-prd。
2. 组织成员权限：决定用户属于哪个组织，以及能访问组织工作区。

新增的业务能力权限位于两者之后：

```text
登录身份有效
    ↓
Agent 权限已开通
    ↓
组织成员关系有效
    ↓
命中部门业务权限策略
    ↓
可使用 UAT 环境控制
```

后台 `admin` 角色只表示可以进入 Admin 和管理权限策略，不应自动等价于拥有全部业务能力。若确实需要管理员排障，可增加单独的、带审计记录的超级管理员覆盖能力。

## 4. 首期权限策略模型

### 4.1 一条策略包含的字段

| 字段 | 说明 |
| --- | --- |
| 策略 ID | 系统生成的唯一标识 |
| 策略名称 | 例如“研发中心-测试造数” |
| 组织 | 例如 CoinEx |
| 能力 | 首期为“测试造数” |
| 部门范围 | 一个或多个 OA 部门 |
| 是否包含子部门 | 建议默认开启 |
| 授权范围 | `UAT 环境控制`（首期固定为系统当前开放的全部任务） |
| 状态 | 启用、停用 |
| 有效期 | 可选的开始时间和结束时间 |
| 说明 | 申请背景、使用目的等 |
| 审计字段 | 创建人、修改人、创建时间、修改时间 |

首期只实现“允许”策略：

- 命中任意一条启用策略即可允许。
- 多条策略命中时均授予 `UAT 环境控制`；未来增加任务级范围后再取任务并集。
- 停用策略即可撤销授权。
- 暂不实现显式拒绝策略，避免引入优先级冲突。

### 4.2 推荐的初始策略

```text
策略名称：研发中心-测试造数
组织：CoinEx
部门：研发中心
包含子部门：是
能力：测试造数
授权范围：UAT 环境控制
状态：启用
```

首期不在 Admin 中拆分资产调整、风控权限、2FA 操作等平台内部任务；这些任务仍受系统级任务黑名单和后端安全校验约束。未来需要更细粒度控制时，再引入任务级策略。

## 5. Admin 页面设计

新增一级菜单：`高级权限管理`，放在 `Agent 审核` 后面。

### 5.1 权限策略列表

列表展示：

- 策略名称
- 组织
- 能力
- 部门范围
- 授权范围（UAT 环境控制）
- 状态
- 有效期
- 最近修改人和时间

操作：

- 新增策略
- 点击策略查看只读详情
- 编辑策略
- 点击状态直接启用/停用策略
- 删除策略（软删除，保留审计记录）
- 查看审计记录
- 查看命中用户数量

删除后策略不再参与权限判断，历史审计记录继续保留；编辑态需要与新建态有明显视觉区分。

### 5.2 策略查看与新增/编辑

进入“高级权限管理”时默认不展示编辑表单：

- 点击策略进入只读查看模式，展示组织、部门、UAT 环境控制、状态、有效期、说明和审计记录。
- 点击“新增策略”才进入新建编辑模式。
- 点击“编辑”进入编辑模式，编辑容器需要与只读模式有明显视觉区分。

表单分为三部分：

#### 授权对象

- 组织选择
- OA 部门树选择
- 是否包含子部门

部门必须从 OA 同步的部门树中选择，不允许手工输入部门名称。

#### 授权能力

- 测试造数

能力目录由系统代码维护，Admin 只能选择已注册的能力，不能任意输入能力字符串。

#### 授权范围

- UAT 环境控制

Admin 首期不展示测试造数平台内部的单个任务代码。授权后，用户可使用系统当前开放的 UAT 环境和造数任务；被系统级黑名单阻断的任务不能通过部门策略重新开放。

### 5.3 用户权限检查

页面提供“检查用户权限”入口，按邮箱或姓名选择用户后展示：

- 当前账号状态
- Agent 权限
- 组织成员关系
- OA 当前部门路径
- 命中的策略
- 可用能力
- UAT 环境控制状态
- 拒绝原因

示例：

```text
用户：casey.lin@corp.test
部门：研发中心 / xxx组
能力：测试造数       允许
命中策略：研发中心-测试造数
UAT 环境控制：允许
```

如果没有命中：

```text
能力：测试造数       拒绝
原因：当前部门未命中任何启用的测试造数策略
```

## 6. 部门数据来源与匹配规则

### 6.1 OA 是权威来源

部门权限不能依赖用户自己填写，也不能依赖管理员手工维护用户部门。

当前代码中的 `department_name` 可以继续作为展示字段，但权限匹配应优先使用 OA 的稳定部门标识或完整部门路径。部门名称可能重名或调整，不应作为唯一长期主键。

### 6.2 子部门匹配

策略选择“研发中心”且开启“包含子部门”时，以下用户均可命中：

- 研发中心本部门
- 研发中心 / 后端组
- 研发中心 / Web 组
- 研发中心 / 测试开发组

匹配应基于 OA 部门 ID 或带边界的完整路径，不能使用简单的字符串包含，避免误匹配“研发中心外包组”等相似名称。

### 6.3 OA 不可用时的处理

对于受部门限制的能力：

- OA 成功加载：按当前目录结果判断。
- OA 暂时不可用且没有可信的安全缓存：拒绝本次受限能力访问，并返回“部门信息暂时无法确认”。
- 不应使用仅用于页面展示的过期部门缓存放行高风险造数操作。

一般页面展示可以继续使用现有缓存策略，但安全授权和展示数据需要区分。

## 7. 后端授权流程

建议新增统一的业务能力授权服务，例如：

```text
check_capability_access(
    user,
    organization_key,
    capability_key,
    task_name=None,
) -> AccessDecision
```

返回结果至少包含：

- `allowed`
- `reason`
- `matched_policy_id`
- `matched_policy_name`
- 当前部门快照

### 7.1 测试造数工具

当前 `TEST_DATA_ADMIN_ONLY` 的单一管理员判断应逐步替换为部门策略判断：

1. 会话创建或新一轮请求时，判断用户是否拥有 `UAT 环境控制` 能力。
2. `list_test_data_capabilities` 返回系统当前开放的环境和任务目录。
3. `prepare_test_data` 校验 `UAT 环境控制` 能力。
4. `execute_test_data` 再次校验 `UAT 环境控制` 能力。
5. 权限被撤销后，已有但未执行的计划不能继续执行。

环境列表仍按系统级配置返回，不参与部门策略判断。

### 7.2 权限默认值

- 没有命中任何策略：拒绝。
- 部门信息为空或无法确认：拒绝受限能力。
- 任务被系统级黑名单阻断：拒绝，Admin 策略不能覆盖。
- 策略已停用或过期：不参与匹配。

## 8. 数据模型建议

建议新增以下业务表，具体字段可在实现阶段结合现有 SQLite 结构调整。

### 8.1 `permission_policies`

保存策略主体信息：

- `policy_id`
- `policy_name`
- `organization_id`
- `capability_key`
- `task_scope_type`：`all` 或 `selected`
- `status`
- `starts_at`
- `expires_at`
- `description`
- `created_by`
- `updated_by`
- `created_at`
- `updated_at`

### 8.2 `permission_policy_departments`

保存策略与部门的关系：

- `policy_id`
- `department_key`
- `department_path_snapshot`
- `include_children`

使用独立关系表，便于一条策略配置多个部门，也避免把部门列表塞进 JSON 字段。

### 8.3 `permission_policy_tasks`

首期策略固定为全部系统允许任务，不写入任务明细。该表结构暂不参与 Admin 配置，未来需要任务级授权时再启用：

- `policy_id`
- `task_name`

当前所有策略使用 `task_scope_type=all`，无需写入任务明细。

### 8.4 `permission_decision_logs`

记录关键授权结果：

- 用户和组织
- 能力和任务
- 允许/拒绝
- 命中的策略
- 部门快照
- 拒绝原因
- session/turn/request 标识
- 决策时间

造数执行日志和权限决策日志分开保存，便于区分“没有权限”和“有权限但上游执行失败”。

## 9. 迁移与兼容策略

1. 保留 `TEST_HELP_TOKEN`、系统级任务黑名单和系统级环境白名单，它们仍是平台安全边界。
2. 新权限策略上线后，默认没有部门策略的用户不能使用测试造数。
3. 不再把 `TEST_DATA_ADMIN_ONLY=true` 作为最终业务授权模型；该配置可在迁移期间作为总开关，但不能替代部门策略。
4. 现有组织管理员不应自动获得所有测试造数任务；迁移时应明确生成管理员策略，或者通过显式超级管理员权限处理。
5. 现有 Agent 权限、组织成员和工作区权限不改变。

## 10. 验收标准

- Admin 可以创建、编辑、启用/停用和删除测试造数部门策略。
- Admin 不能手工输入不存在的部门，部门选项来自 OA 部门目录。
- 研发中心用户可以使用命中策略允许的 UAT 环境控制能力。
- 非命中部门用户无法看到或调用测试造数能力。
- 部门调整后，新的权限判断使用新的 OA 部门归属。
- 策略停用后，新的准备请求和已有未执行计划都不能执行。
- 系统级黑名单任务始终不能通过部门策略开放。
- 权限检查页面能说明允许或拒绝的具体原因。
- 所有策略变更和关键权限决策均可追溯到操作人和时间。
- 不同测试环境之间不需要单独配置权限，系统级环境开放列表继续生效。

## 11. 后续扩展方向

只有出现真实需求时再增加：

- 环境级权限范围
- 指定用户例外授权
- 用户组授权
- 显式拒绝策略
- 审批流
- 按风险等级或金额限制任务

本期不为这些扩展增加前端配置项或通用策略表达式。
