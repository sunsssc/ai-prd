# 跨仓库关联 PR 联合审查

自动触发和手动发起的代码审查都会读取主 PR 描述中的显式关联小节。例如：

```markdown
## Related PRs
- https://github.com/example-org/api/pull/123
- https://github.com/example-org/web/pull/456
```

标题也支持 `关联 PR`、`关联PR`、`Related pull requests`。每项写完整 GitHub HTTPS PR 链接；Markdown 链接、`/files`、`/commits`、查询参数和锚点均可。无关联时省略小节，或写 `None` / `无`。正文其他位置、代码围栏和 HTML 注释里的示例不作为关联。

## 获取和范围

- 主 PR 与关联 PR 的仓库必须已在 `code-auto-review.json` 的 `repositories` 中启用，且属于同一 `organization_key`。未显式配置组织时，沿用上下文准备器从 workspace 仓库路径推导的组织。链接本身不会授予访问权限。
- 每个仓库使用自己的 `github_access` 配置获取 PR。关联 PR 可以是开放且非 Draft 的 PR，或已合并 PR；关闭但未合并、Draft、目标分支不在配置范围内均拒绝。
- 小节最多列 8 个不同 PR，重复链接忽略，主 PR 自身的链接不重复准备。不会递归展开关联 PR 描述里的其他 PR。非法链接、超限或不可用的关联使任务失败，不静默降级为单 PR 审查。
- 每个 PR 准备完整、固定 SHA 的 base/head worktree、独立 diff、变更清单、PR 描述和可用的 ClickUp 需求。原工作仓库的分支不切换。

## 两阶段审查与交付

探索与独立核验都获得相同的主 PR 和关联 PR 上下文。审查指令要求逐个覆盖各仓库，再对照接口、字段、状态和迁移顺序；每条发现带仓库、PR 和路径。关联不代表这些版本已经同时上线，部署前提未知时须说明。

交付前重新获取主 PR 和关联 PR；base 分支、base/head SHA、描述或状态发生变化时，整项任务失败，不写入新报告或创建报告邮件任务。获取失败也不交付。失败任务可通过现有重试入口重新获取上下文；主 PR 的 head 改变时需为新 head 发起任务。

成功时只产生一份联合报告，并由服务端附上完整的仓库、PR、base/head SHA 表。沿用主任务的通知策略：自动任务通知主 PR 作者，手动任务不额外发邮件；不会因关联关系通知其他作者。失败告警仍沿用原有配置。

这是一次运行的快照审查。调度仍按主 PR/head 去重；已完成任务不会因为关联 PR 单独更新而自动重跑，现有重试接口也只接受失败任务。关联变化监控和已完成任务重审不在本版本范围内。聊天助手里的单 PR 上下文准备接口也保持原有行为。

## 验证口径

`tests/test_related_prs.py` 检查小节解析、去重、非法链接和数量上限。`tests/test_code_reviews.py` 使用真实本地 Git 仓库和假 GitHub/模型运行时验证双仓库固定版本、两个阶段的上下文、各仓库客户端、交付前变化检测，以及缺失/不允许的上下文不交付。

这些工程测试验证流程，不证明模型能识别多少跨仓库缺陷。README 和案例中的 20-PR 开发集指标对应此前的两阶段评测，不作为本功能的质量或人工工时指标。
